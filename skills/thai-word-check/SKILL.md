# ตรวจคำไทยก่อน Implement

หลักการข้อเดียว: **คำที่ระบบมีอยู่แล้วชนะเสมอ** ผู้ใช้เรียนรู้คำของระบบไปแล้ว การเปลี่ยนคำโดยไม่จำเป็นทำให้สับสน (Nielsen #4 Consistency and standards)

สกิลนี้ใช้ได้กับทุกโปรเจกต์ ไม่จำกัดงานการเงิน

## คำที่ใช้เรียกไฟล์ในสกิลนี้

- **glossary ของโปรเจกต์** — ไฟล์คำศัพท์ที่อยู่ใน repo ของโปรเจกต์เอง (เช่น `docs/glossary.md`) เป็นที่เก็บคำเฉพาะโปรเจกต์
- **ไฟล์ตัวอย่างโปรเจกต์** — `references/projects/<ชื่อโปรเจกต์>.md` ในสกิลนี้ อ่านอย่างเดียว ใช้เสริมสำหรับคำที่ glossary ของโปรเจกต์ยังไม่มี
- **glossary กลาง** — `references/glossary.md` ในสกิลนี้ คำที่ใช้ได้ทุกโปรเจกต์

## ลำดับความสำคัญของคำ

1. **คำที่ระบบใช้อยู่** (UI, โค้ด, เอกสาร, test) — ใช้ตามนั้นเป๊ะ รวมถึงตัวสะกดและวรรค
2. **glossary ของโปรเจกต์** → **ไฟล์ตัวอย่างโปรเจกต์** → **แม่แบบข้อความ** (`references/message-patterns.md` เฉพาะข้อความประเภทที่แม่แบบครอบคลุม) → **glossary กลาง** ดูทุกแหล่ง ถ้าขัดกันแหล่งที่อยู่ก่อนชนะ
3. **คำใหม่** — เมื่อข้อ 1–2 ไม่มีคำให้ใช้ ต้องเสนอให้ผู้ใช้เห็นในรายงาน (ขั้นตอน 5) โดยเขียนที่มาว่า `(ใหม่)` เลือกตามลำดับนี้:
   1. คำที่คนทั่วไปพูดกัน — สั้น ชัด ไม่ต้องแปลศัพท์
   2. ศัพท์ทางการ/กฎหมาย/ราชบัณฑิต — ใช้เมื่อจำเป็นเท่านั้น และต้องมีคำอธิบายสั้น ๆ ข้างกัน
   3. คำที่ AI ตั้งเอง — ทางเลือกสุดท้าย

**คำใหม่** หมายถึงคำหรือวลีที่ไม่พบทั้งในระบบและในแหล่งใดของข้อ 2 วลีที่ประกอบจากคำที่มีอยู่แล้ว (เช่น "ลบ" + "เอกสาร" = "ลบเอกสาร") และข้อความที่ทำตามแม่แบบข้อความ ไม่นับเป็นคำใหม่ ข้อยกเว้น: ชื่อฟีเจอร์ ชื่อเมนูหลัก หรือแบรนด์ที่ระบบยังไม่มี นับเป็นคำใหม่เสมอ แม้จะประกอบจากคำที่มีอยู่แล้ว (เช่น "เอกสารที่ลบแล้ว") หรือเป็นคำที่คนทั่วไปคุ้น (เช่น "ถังขยะ")

## ขั้นตอน (ทำก่อนเขียนโค้ดหรือข้อความใด ๆ)

### 0. ระบุโปรเจกต์
1. ชื่อโปรเจกต์ = ชื่อโฟลเดอร์รากของ repo ที่ไฟล์งานอยู่ frontend กับ backend ของแอปเดียวกัน (เช่น `web/` กับ `app/`) นับเป็นโปรเจกต์เดียว ถ้า repo รวมหลายแอปที่มีหน้าจอและผู้ใช้แยกกัน ให้ใช้ชื่อโฟลเดอร์ของแอปที่กำลังแก้ และลองชื่อโฟลเดอร์รากด้วยเมื่อหาไฟล์ในข้อ 3
2. หา glossary ของโปรเจกต์ใน repo: ไฟล์ที่ชื่อขึ้นต้นด้วย `glossary` หรือ `คำศัพท์` (ไม่สนตัวพิมพ์เล็กใหญ่ นามสกุลใดก็ได้ เช่น `GLOSSARY.md`, `docs/glossary.md`) ที่รากหรือใน `docs/` ถ้ามี ให้เปิดอ่าน
3. เปิด `references/projects/<ชื่อโปรเจกต์>.md` ของสกิลนี้ด้วยถ้าชื่อตรงกัน (ไม่ว่าจะเจอ glossary ของโปรเจกต์หรือไม่)
4. ถ้าไม่มีทั้งสองอย่าง หรือระบุชื่อโปรเจกต์ไม่ได้ ให้ใช้ glossary กลางอย่างเดียว
5. จดไว้ว่าใช้แหล่งไหนบ้าง เพื่อเขียนในบรรทัด "ข้อสังเกต" ของรายงาน (ขั้นตอน 5)

### 1. รวบรวมคำที่งานนี้จะแตะ
อ่านงานที่ได้รับ แล้วลิสต์ทุกข้อความไทยที่จะเพิ่ม/แก้: ปุ่ม, เมนู, หัวข้อ, label, placeholder, ข้อความว่าง (empty), กำลังโหลด, สำเร็จ, error, ยืนยัน, tooltip, คำอธิบาย, ข้อความใน prompt ของ AI, ชื่อเทสต์

### 2. ค้นหาว่าระบบใช้คำนี้อยู่แล้วหรือยัง
- ค้นทั้งโปรเจกต์ด้วยเครื่องมือค้นข้อความที่มี (เช่น grep, ripgrep) ในไฟล์ซอร์ส ไฟล์แปลภาษา (i18n) และเอกสารของโปรเจกต์ ทั้ง **คำตรง** และ **คำพ้อง** (ดูตาราง "คำพ้องที่ต้องค้นด้วย" ใน glossary กลาง)
- ภาษาไทยไม่มีช่องว่างคั่นคำ คำสั้นอย่าง "ลบ" หรือ "ส่ง" จะติดคำอื่นมาด้วย (เช่น "ลบล้าง", "ส่งออก") ให้เปิดดูบรรทัดที่เจอ แล้วนับเฉพาะจุดที่เป็นข้อความที่ผู้ใช้เห็นและมีความหมายตรงกัน
- ค้นสคีมา/ชื่อฟิลด์/enum ด้วย เพราะคำในโค้ด (อังกฤษ) มักผูกกับคำไทยหนึ่งคำ
- ถ้าค้นไม่เจอข้อความไทยเลย ให้ตรวจว่าโปรเจกต์เก็บข้อความไว้ที่อื่นหรือไม่ (ไฟล์แปลภาษา, ฐานข้อมูล, CMS) ถ้าเข้าไม่ถึง ให้เขียนในรายงานว่าตรวจกับระบบจริงไม่ได้
- ผลลัพธ์ที่ต้องได้: "คำนี้มีแล้ว ใช้ว่า X อยู่ N จุด" หรือ "ยังไม่มี"

### 3. ตัดสินใจรายคำ
| เจอแบบไหน | ทำอะไร |
|---|---|
| มีคำเดียวในระบบ | ใช้คำนั้น |
| มีหลายคำสำหรับสิ่งเดียวกัน (เช่น "ตั้งค่า" / "การตั้งค่า") | เลือกคำที่ใช้บ่อยสุดจากจุดที่นับในขั้นตอน 2 + แจ้งผู้ใช้ว่ามีคำซ้ำ ไม่แก้ของเก่านอกขอบเขตงาน |
| ไม่มีในระบบ แต่มีใน glossary แหล่งใดแหล่งหนึ่ง | ใช้ตาม glossary |
| ไม่มีที่ไหนเลย (คำใหม่) | เสนอ 1 คำ (สั้น เข้าใจง่าย) พร้อมเหตุผลหนึ่งบรรทัด ใส่ในรายงานว่า "(ใหม่)" |
| คำเดียวกันแต่ความหมายต่างบริบท | ห้ามใช้ปนกัน แยกคำหรือเติมคำขยาย |

### 4. ตรวจด้วยเช็กลิสต์ก่อนเขียน
เปิด `references/checklist.md` แล้วตรวจให้ผ่านครบทุกข้อที่เกี่ยวกับข้อความนั้น (เช่น ข้อรูปแบบเงิน/วันที่ ข้ามได้ถ้าข้อความไม่มีตัวเลข) ถ้าต้องเขียนข้อความสำเร็จ/ผิดพลาด/ว่าง/ยืนยัน ให้ใช้แม่แบบใน `references/message-patterns.md`

### 5. รายงานสั้น ๆ ก่อนเริ่ม implement
แสดงตารางนี้ให้ผู้ใช้เห็น ทุกข้อความที่ลิสต์ไว้ในขั้นตอน 1 ต้องมีหนึ่งแถว รวมถึงข้อความเต็มประโยค (เนื้อหาหน้าต่าง, ข้อความสำเร็จ, error):

```
คำที่ใช้ → ที่มา → หมายเหตุ
ส่งคำถาม → src/app/page.tsx:120 → ใช้อยู่แล้ว 4 จุด
ลบรายการ → glossary กลาง → ระบบยังไม่มีปุ่มลบ
ไม่ลบ → แม่แบบข้อความ → ปุ่มปิดหน้าต่างยืนยัน
ถังขยะ → (ใหม่) → เสนอ เพราะระบบและ glossary ยังไม่มีคำเรียกที่เก็บของที่ลบชั่วคราว
ข้อสังเกต: ใช้ glossary กลางอย่างเดียว โปรเจกต์ยังไม่มี glossary; พบ "ตั้งค่า" กับ "การตั้งค่า" ใช้ปนกัน
```

ช่อง "ที่มา" เขียนได้ 6 แบบ: `ไฟล์:บรรทัด` (คำในระบบ), `glossary ของโปรเจกต์`, `ไฟล์ตัวอย่างโปรเจกต์`, `glossary กลาง`, `แม่แบบข้อความ`, หรือ `(ใหม่)` บรรทัด "ข้อสังเกต" ใส่แหล่ง glossary ที่ใช้ คำซ้ำที่พบ และสิ่งที่ตรวจไม่ได้ รายงานนี้ยังไม่ถามเรื่องบันทึก glossary (ถามในขั้นตอน 6)

**หยุดรอคำตอบผู้ใช้ก่อน implement เฉพาะเมื่อ**:
- คำสองแบบมีความหมายทางกฎหมาย/การเงินต่างกัน
- งานนี้ตั้งชื่อฟีเจอร์ ชื่อเมนูหลัก หรือแบรนด์ที่ระบบยังไม่มี ไม่ว่าจะตั้งด้วยคำแบบไหน (ป้ายปุ่มและข้อความทั่วไปของฟีเจอร์ใหม่ไม่นับ)
- ระบบใช้หลายคำและนับแล้วใกล้เคียงกันจนเลือกไม่ได้

กรณีอื่นให้เริ่ม implement ด้วยคำในตารางได้เลย

### 6. หลัง implement
- ค้นซ้ำว่าคำที่เขียนตรงกับตารางที่รายงาน ไม่มีคำหลุด/สะกดผิด/ปนอังกฤษที่ไม่จำเป็น
- ถ้ารายงานมีคำที่ทำเครื่องหมาย "(ใหม่)" ให้ถามผู้ใช้หนึ่งครั้งว่าจะบันทึกลง glossary หรือไม่ ตามกฎด้านล่าง ในคำถามให้ระบุทุกคำใหม่พร้อมไฟล์ที่จะบันทึก (และไฟล์ที่จะสร้างใหม่ ถ้ามี) คำตอบรับของผู้ใช้ต่อคำถามนี้นับเป็นคำสั่งให้เขียนเฉพาะไฟล์ที่ระบุไว้ในคำถาม ถ้าไม่มีคำใหม่ ไม่ต้องถาม

## กฎการบันทึกคำใหม่

**ห้ามเขียนไฟล์ glossary ใด ๆ ก่อนผู้ใช้ยืนยัน** คำที่ AI ตั้งเองยังไม่ใช่คำของระบบจนกว่าผู้ใช้จะรับ

| คำแบบไหน | บันทึกที่ไหน (หลังผู้ใช้ยืนยัน) |
|---|---|
| คำเฉพาะโปรเจกต์ | glossary ของโปรเจกต์ใน repo ของโปรเจกต์ ถ้ายังไม่มีไฟล์ ให้เสนอสร้าง `docs/glossary.md` โดยใช้โครงของ `references/projects/_template.md` ถ้ามีไฟล์ตัวอย่างโปรเจกต์ ให้คัดลอกตารางคำ ข้อควรระวัง และหัวข้อคำศัพท์อื่นของไฟล์นั้นมาใส่ด้วย แต่ไม่คัดลอกบรรทัดที่บอกว่าไฟล์เป็นไฟล์ตัวอย่าง อ่านอย่างเดียว หรือห้ามแก้ แล้วเพิ่มคำใหม่ที่ผู้ใช้ยืนยัน |
| คำที่ใช้ได้ทุกโปรเจกต์ | glossary กลาง หัวข้อ "คำที่เพิ่มใหม่" ในคำถามของขั้นตอน 6 ต้องระบุชื่อไฟล์นี้ และแจ้งว่าคำที่เพิ่มในโฟลเดอร์สกิลจะหายเมื่อติดตั้งสกิลใหม่ เขียนเมื่อผู้ใช้ตอบรับคำถามนั้นเท่านั้น |

วิธีแยก: คำที่เรียกสิ่งที่มีเฉพาะในแอปนี้ (ชื่อฟีเจอร์ ชื่อเมนู ศัพท์ของธุรกิจนี้) เป็นคำเฉพาะโปรเจกต์ คำปุ่มหรือสถานะทั่วไปที่แอปอื่นก็ใช้ได้ (แบบเดียวกับหัวข้อ 1–3 ของ glossary กลาง) เป็นคำที่ใช้ได้ทุกโปรเจกต์ ถ้าไม่แน่ใจ ให้ถือเป็นคำเฉพาะโปรเจกต์

กฎของไฟล์ตัวอย่างโปรเจกต์:
- ไม่เขียนไฟล์ใน `references/projects/` ของสกิล เพราะโฟลเดอร์สกิลอยู่นอกโปรเจกต์และถูกเขียนทับเมื่อติดตั้งสกิลใหม่
- ถ้าโค้ดปัจจุบันใช้คำอื่นสำหรับความหมายเดียวกับในไฟล์ตัวอย่าง ให้ยึดโค้ด และแจ้งผู้ใช้ในข้อสังเกต
- ถ้าคำในไฟล์ตัวอย่างไม่พบในโค้ดเลย ให้ใช้คำนั้นได้ (ที่มา = `ไฟล์ตัวอย่างโปรเจกต์`) และเขียนในข้อสังเกตว่าไม่พบในโค้ด

## กฎเขียนให้เข้าใจง่ายแต่ครบ

- ประโยคสั้น ภาษาพูดสุภาพ ไม่ใช้ศัพท์แพง ถ้าต้องใช้ศัพท์เทคนิค ให้ใส่คำอธิบายในวงเล็บหนึ่งครั้ง
- ปุ่มใช้ **คำกริยาตามงานที่เกิดจริง** ("บันทึก", "ส่งคำถาม") ไม่ใช้ "ตกลง"/"OK" ลอย ๆ (Nielsen #2 Match with real world) ปุ่มในแถวของรายการที่เห็นชัดว่ากระทำกับอะไร ใช้กริยาคำเดียวได้ ("ลบ") ปุ่มในหน้าต่างยืนยันและปุ่มที่อยู่เดี่ยว ๆ ใช้กริยา + สิ่งที่ถูกกระทำ ("ลบเอกสาร")
- Error บอก 3 อย่าง: เกิดอะไรขึ้น → เพราะอะไร (ถ้ารู้) → ทำอะไรต่อ (Nielsen #9)
- เรื่องที่มีผลสูง (ลบข้อมูล จ่ายเงิน ผลทางกฎหมาย สุขภาพ) ต้องชัดว่าจะเกิดอะไร และไม่ฟันธงเกินข้อมูลที่ระบบมี
- ตัวเลข วันที่ เงิน ใช้รูปแบบเดียวทั้งระบบ (ดู glossary กลาง หัวข้อ "รูปแบบ")
- ไม่ปนไทย-อังกฤษในประโยคเดียวถ้าไม่จำเป็น คำทับศัพท์ที่คนคุ้น (เช่น "ไฟล์", "รหัส OTP") ใช้ได้

## ห้าม

- ห้ามตั้งคำใหม่ทั้งที่ระบบมีคำเดิมอยู่แล้ว
- ห้ามแปลตรงตัวจากอังกฤษถ้าคนไทยไม่ได้พูดแบบนั้น — ไม่ใช้ "ทำการบันทึก" ให้ใช้ "บันทึก"; ไม่ใช้ "ล้มเหลวในการโหลด" ให้ใช้ "โหลดไม่สำเร็จ"
- ห้ามแก้คำเก่านอกขอบเขตงาน — แจ้งเป็นข้อสังเกตแทน
- ห้ามข้ามขั้นตอนนี้เพราะ "ข้อความสั้น" ปุ่มคำเดียวก็ทำให้ระบบไม่ตรงกันได้
